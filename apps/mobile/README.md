# TeamMeet Mobile

Expo React Native app for TeamMeet. This app shares auth, organization, role, validation, and pricing logic with the monorepo packages, while using native mobile navigation, storage, permissions, push notifications, and device integrations.

## Quick start

Run commands from `apps/mobile/` unless noted.

```bash
# Install deps from repo root if needed
cd ../..
bun install

# Start the mobile app
cd apps/mobile
cp .env.example .env.local
bun run start:dev-client
```

Common commands:

```bash
bun run ios                  # Launch iOS dev client
bun run android              # Launch Android dev client with local SDK env helper
bun run web                  # Expo web preview
bun run typecheck            # TypeScript check
bun run lint                 # ESLint; warnings currently exist, errors should block work
bun run test                 # Jest
bun run verify               # typecheck + lint + test
bun run config               # Resolved public Expo config
bun run config:introspect    # Introspected native config/plugin output
bun run android:doctor       # Android SDK/JDK/adb diagnostics
```

## Stack

- Expo SDK 54, Expo Router 6
- React Native 0.81, React 19
- Supabase Auth + AsyncStorage session persistence
- Supabase Postgres/Storage/Realtime through shared generated types
- Jest for lib-level tests
- Sentry for error reporting, PostHog for product analytics
- EAS Build/Submit for store builds

## Environment

Create `apps/mobile/.env.local` from `.env.example`.

Required for normal development:

| Variable | Purpose |
| --- | --- |
| `EXPO_PUBLIC_SUPABASE_URL` | Supabase project URL |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | Supabase anon key |
| `EXPO_PUBLIC_WEB_URL` | Web/API base URL; defaults should point at `https://www.myteamnetwork.com` for production-like flows |
| `EXPO_PUBLIC_TURNSTILE_SITE_KEY` | Captcha key for auth/donation challenge WebViews |

Optional/feature-specific:

| Variable | Purpose |
| --- | --- |
| `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` | Google OAuth web client ID |
| `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` | Google OAuth iOS client ID |
| `EXPO_PUBLIC_POSTHOG_KEY` / `EXPO_PUBLIC_POSTHOG_HOST` | Product analytics |
| `EXPO_PUBLIC_SENTRY_DSN` | Native error reporting |
| `EXPO_PUBLIC_CAPTCHA_BASE_URL` | Captcha widget origin, usually the web URL |

Never commit `.env.local` or production secrets. Only `EXPO_PUBLIC_*` values are available in the client bundle; do not put service-role keys or private API secrets here.

## Project layout

```text
apps/mobile/
├── app/                         # Expo Router routes/layouts
│   ├── (auth)/                  # login, signup, callback, password flows
│   └── (app)/(drawer)/          # authenticated app shell and org-scoped routes
├── src/components/              # reusable UI and feature components
├── src/contexts/                # auth, org, network, color scheme, lock state
├── src/hooks/                   # data hooks and behavior hooks
├── src/lib/                     # Supabase, analytics, notifications, uploads, tokens
├── src/navigation/              # AppDrawer and custom DrawerContent
├── assets/                      # app icons, splash, brand artwork
├── plugins/                     # Expo config plugins
├── scripts/                     # local developer helpers
├── docs/                        # store/privacy/release notes
├── app.json                     # primary Expo/native config
├── app.config.ts                # config-time helpers
├── eas.json                     # EAS build/submit profiles
├── metro.config.js              # monorepo-aware Metro config
```

Native folders (`ios/`, `android/`) are generated by Expo prebuild/EAS. Prefer changing `app.json`, `app.config.ts`, or `plugins/` rather than hand-editing generated native files.

## Routing and navigation

Provider flow:

```text
ColorSchemeProvider
  → AuthProvider
  → NetworkProvider
  → GestureHandlerRootView
  → ToastProvider
  → Expo Router Stack
```

Route groups:

| Route | Purpose |
| --- | --- |
| `app/(auth)` | unauthenticated auth screens |
| `app/(app)` | authenticated shell with org context |
| `app/(app)/(drawer)` | org list, profile, terms, account deletion, drawer shell |
| `app/(app)/(drawer)/[orgSlug]/(tabs)` | primary org tab loop: home, calendar, announcements, members, menu |
| `app/(app)/(drawer)/[orgSlug]/*` | feature stacks: chat, events, donations, jobs, parents, settings, search, etc. |

Use Expo Router paths for navigation. If a shell command references paths with parentheses or brackets, quote the path.

## UI conventions

Use the mobile design system instead of web/Tailwind patterns.

- Styling: `useThemedStyles`, `src/lib/design-tokens.ts`, `src/lib/typography.ts`, `src/lib/chrome.ts`
- Prefer `Pressable` over `TouchableOpacity`
- Prefer `expo-image` over React Native `Image`
- Prefer `SafeAreaView` from `react-native-safe-area-context`
- Use `LinearGradient` for chrome/header gradients
- Use `lucide-react-native` for icons
- Use `@gorhom/bottom-sheet` for native bottom sheets
- Keep Supabase nullability explicit and render safe defaults

Typical org screen structure:

```tsx
<View style={styles.container}>
  <LinearGradient colors={[APP_CHROME.gradientStart, APP_CHROME.gradientEnd]}>
    <SafeAreaView edges={["top"]}>
      {/* org logo opens drawer */}
      {/* screen title/action area */}
    </SafeAreaView>
  </LinearGradient>

  <View style={styles.contentSheet}>{/* screen content */}</View>
</View>
```

## Data, auth, and offline behavior

- Supabase client lives in `src/lib/supabase.ts`.
- Mobile auth uses AsyncStorage persistence and PKCE; it does not use web cookies.
- Hooks in `src/hooks/` usually follow stale-while-revalidate behavior with `refetchIfStale()` on focus and `refetch()` on pull-to-refresh.
- Realtime hooks subscribe to Supabase `postgres_changes` and clean up on unmount.
- Soft-delete-aware queries must filter `.is("deleted_at", null)` where applicable.
- Optional Supabase RPC params should use `undefined`, not `null`.

## Testing expectations

Current Jest coverage is strongest for pure functions, auth helpers, analytics, permissions, and regression tests. Native UI flows should be validated with a dev client or EAS preview build.

Before opening a mobile PR, run:

```bash
bun run typecheck
bun run lint
bun run test
```

Current lint policy allows warnings, but new work should not add warnings. Existing warnings are mostly React Native style-rule noise and should be cleaned up incrementally.

- Lint currently passes with warnings; reduce warning count as files are touched.
- Keep `docs/data-safety.md` current before every Play Store submission.
- When adding native permissions, update `app.json`, store data-safety notes, and verify with `bun run config:introspect`.
- When adding analytics events, avoid sending sensitive free-text values unless explicitly reviewed.
